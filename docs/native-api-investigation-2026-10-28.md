# 原生播放空响应与参考项目更新调查（2026-10-28）

## 后续实验：已找到可验证的修复路径

以下原始调查结论保留，反映本轮逐项实验前的状态。随后使用同一失败分集进行对照，发现原项目生成的随机身份通常空响应，而参数一致的设备登记流程取得的身份可持续返回原生播放模型。第 78、155 集均取得对应 1080p 轨道并完成媒体处理，重建连接后仍可取得第 1、2、78、155 集资源。单次更改版本曾成功，但重复实验失败，不能将版本变更认定为修复。

参考项目原样登记混用了抖音包名和红果 aid，未取得有效身份；一致的红果参数登记成功。服务端实际返回 16 位身份，旧代码只接受 19 位，现已修正。现有证据确认身份登记是有效恢复路径，但不声称已了解服务器内部全部校验规则。详见 [0.6.2 修复说明](releases/v0.6.2.md)。

## 原始调查结论与边界

当前故障可定位到取得原生播放模型的 HTTP 请求阶段：原生批量播放接口返回 HTTP 200，但响应体为 0 字节，播放器尚未获得媒体地址。与官网兼容接口对部分后续分集返回的 403 是两个不同故障表现，不能混为一谈。

多个参考项目存在相同或相近故障报告，说明并非本项目独有。当前证据支持继续调查上游请求协议兼容性、设备身份校验及签名链路，但不足以确定服务器内部具体拒绝条件。没有找到经本项目实测能恢复目标分集的更新；本轮不修改生产协议，不声称恢复全集。

## 协议差异与实际验证

monorepo 参考实现包含设备注册、播放请求签名、媒体类型 1004，以及 video_model.fallback_api 的后续解析。本项目持久化身份由本地生成，原生批量播放使用媒体类型 1，播放分支与榜单分支的签名处理不同。参考版本号也不同。这些是待验证差异，并非已确认根因；在响应体为空时，后续模型解析逻辑尚未执行。

本轮沿用同一持久化本机身份，不轮换身份、不复制第三方标识。对先前失败的第 78 集进行以下对照，记录时间为 2026-10-28 02:31:21 UTC：

| 请求变体 | HTTP 状态 | 响应字节 | 目标播放模型 |
| --- | ---: | ---: | --- |
| 当前原生批量请求 | 200 | 0 | 无 |
| 添加当前 _rticket、ts 时间参数 | 200 | 0 | 无 |
| 在时间参数基础上改用参考媒体类型 1004 | 200 | 0 | 无 |
| 上述请求再加入现有 Java 签名器结果 | 200 | 0 | 无 |

因此，单纯补时间字段、改媒体类型或加入现有签名结果均未恢复；最后一项也不能排除签名算法或签名上下文本身不兼容。设备注册身份与版本组合尚未形成可用对照，不能断言是哪一项导致空响应。

此前对照还覆盖 a/b 内容域名、代理与直连、独立单集请求，均未恢复。当前模型响应已为空，因此播放器解码或 JSON 字段解析不是本次“0 字节”产生的位置；不能进一步据此排除所有客户端请求构造问题。
