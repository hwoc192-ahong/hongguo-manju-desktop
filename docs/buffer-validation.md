# 滚动缓冲验收

日期：2026-10-19，版本 0.2.6，Windows x64。

## 改动依据

原媒体流程在当前集播放前依次取得资源、下载完整输入、完整转码。每次换集都会重新走这一流程，解释了持续等待的原因。此次保持已验证的解码方式，将后续剧集的下载和转码提前完成，并复用完成后的本地文件。

## 回归测试

`npm test`：78 项通过，其中新增 9 项媒体缓冲测试，覆盖：

- 当前集优先，后台依次准备后四集，窗口从 1–5 移到 2–6。
- 已完成缓存直接复用，正在缓冲的同一集接管任务，不重复下载。
- 跳集取消过时下载及正在执行的转码，当前集优先；退出详情页与应用时停止任务。
- 取消不重试、清理临时文件；后台失败最多尝试两次并继续其他集，用户可手动重试。
- 五集窗口不被清理，旧缓存按 1 GiB 目标淘汰；重开后复用完整缓存。
- IPC 最多接收五个有效、不同的剧集编号。

原有媒体强制刷新、退出时禁止启动 FFmpeg、退出期间晚返回资源不能再下载等测试均通过。更新器回归继续验证发现新版不下载、用户点击才下载、安装需再次确认。

`npm run typecheck`、`npm run build` 通过。

## 真实播放器验收

执行 `node scripts/buffer-qa.mjs`，在隔离目录生成 10 秒视频及音频，使用真实 Electron、生产 preload、MediaCache、本地 HTTP 下载及随包 FFmpeg，不替换实际缓存和转码逻辑。

2026-10-19 测试结果：

- 第 1 集先完成准备并播放，后台顺序完成 2–5 集；HTTP 请求与实际剧集顺序一致。
- 进入第 2 集直接复用已完成文件，准备调用约 0.02 ms；后台补第 6 集。这里测量的是主进程缓存查询，不代表屏幕出画延迟。
- 第 2 集自然结束后自动播放已缓存第 3 集，并补第 7 集；全过程保持同一全屏元素。
- 跳至第 8 集时窗口只包含最后一集；返回首页时窗口为空。
- renderer 无未捕获异常。

机器报告位于本机 `outputs/buffer-qa-1792396661230/report.json`。另外 `node scripts/fullscreen-qa.mjs` 再次通过控制栏隐藏/恢复、手动上下集、两次自然结束连播、退出全屏后换集、暂停显示控件等检查，报告位于 `outputs/fullscreen-qa-1792396667890/report.json`。

## 范围与限制

上述测试验证真实下载、转码、缓存、IPC、界面和全屏生命周期；媒体为本地生成的测试视频，没有据此声称已重新验收全部线上作品。首次未缓存的剧集依然需要准备；网络或 CPU 跟不上观看时会等待。缓存完成文件以约 1 GiB 为清理目标，临时文件另需空间，Windows 占用中的旧文件在后续清理时重试。

内容资源查询取消后可能仍在底层完成一次短接口请求，但其结果不会再触发视频下载。后台准备在详情页内持续进行，包括暂停和关闭自动连播的情况。它与应用更新下载互不影响。
