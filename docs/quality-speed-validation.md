# 清晰度与倍速修复验收

日期：2026-10-23，版本 0.2.9，Windows x64。

## 原因及处理

旧版轨道优先级为 540p → 720p → 480p → 360p → 1080p。各集可解码轨道分布不同，可能有的集被选为 540p，有的集只能选可解码的 1080p，形成程序造成的分辨率变化。新版本保留编码兼容性过滤，按 1080p → 720p → 540p → 480p → 360p 选择。播放器显示实际分辨率，不能把仅有低清的来源承诺为高清。

本地兼容转码保持源分辨率（奇数边长仅取相邻偶数），CRF 从 25 调整至 20，减少额外压缩损失。缓存增加策略标记；旧策略文件在初始化时清理，新的完整缓存可跨重启复用。不会清理收藏、观看进度或播放标识。高清可能增加首次准备时间、网络流量和磁盘需求。

旧版每集 Player 均重新初始化 rate=1；现在倍速由 App 层保存并传递，使用本机 localStorage 持久化。手动换集、自动连播、切换作品和进程重启后继续应用；存储不可写时本次会话仍生效，并提示保存失败。

## 回归

排序和旧缓存用例在修改前失败；真实 Electron 倍速回归在旧代码失败，断言为“手动下一集后仍为 1.5”，实际为 1。

修改后 `npm test` 85 项通过，`npm run typecheck` 和生产构建通过。覆盖高分辨率优先、输入轨道排序变化、缺失高分辨率时回退、未知与不支持编码、旧策略缓存失效、新缓存重启复用，以及倍速无效值和存储故障处理。

`node scripts/fullscreen-qa.mjs` 使用生成的本地视频验证 1.5 倍手动上下集、两次自然结束自动连播、真实应用进程重启及随后改为 2 倍换集。全屏浮层隐藏、暂停显示及保持同一全屏元素均通过，报告为本机 `outputs/fullscreen-qa-1792720179218/report.json`。

`node scripts/buffer-qa.mjs` 使用生产 preload、MediaCache、真实 HTTP 和随包 FFmpeg，再次通过五集准备、缓存复用、补入第六/七集、跳集与离页清理，报告为本机 `outputs/buffer-qa-1792720195357/report.json`。

## 线上与打包程序抽查

实际请求样本作品的第 1、2、78、155 集资源元数据：均提供 360p 至 1080p，多数低分辨率为当前不支持的 bytevc2，1080p 为支持的 bytevc1。新选择均为 1080p。该样本旧版也可能已选择 1080p，不能把所有主观模糊都归因于同一个原因；排序回归另用可解码的多清晰度轨道验证。

运行 `node scripts/quality-speed-qa.mjs`，目标为 0.2.9 打包程序，使用隔离数据目录与真实内容网络：

| 操作 | 解码画面 | 实际倍速 |
| --- | --- | --- |
| 样本作品第 1 集 | 1920×1080 | 初始 1 倍 |
| 选择 1.5 倍，手动下一集至第 2 集 | 1920×1080 | 1.5 倍 |
| 第 2 集跳至结尾触发自然结束，连播第 3 集 | 1920×1080 | 1.5 倍 |
| 手动选第 78 集 | 1924×1080 | 1.5 倍 |
| 切换另一作品《十元盒饭，卷懵吃了不烧心》第 1 集 | 1922×1080 | 1.5 倍 |
| 改为 2 倍，关闭并重新启动进程后打开作品 | 实际播放器及选择框核对 | 2 倍 |

上述播放均有视频帧与音频解码，界面均显示 1080p，renderer 无未捕获异常。不同作品源宽高可能略有差异，保留源比例。机器报告和截图位于本机 `outputs/quality-speed-live-2026-10-23/`，来源元数据摘要位于 `outputs/quality-source-2026-10-23/`，不发布媒体地址、密钥或安装标识。

打包后的主进程、preload、页面及资源与已测试构建逐文件一致。未在全新 Windows 机器上验收，音频为解码验证而非人工试听，未对来源主观画质或全部线上作品作保证。更新器行为保持“点击后才下载安装包”。
